# Krea 2 프롬프트 문법 조사 (2026-10-04)

조사 목적: Krea2 Turbo Prompt Studio 업그레이드의 기준값 확정.
확신도 표기: ✅ 공식 원문 직접 확인 / 🟡 제3자 자료(공식 아님) / ❓ 미확인.

## 0. 사용자 실측 (공식·제3자 자료보다 우선)
- LoRA 트리거는 **맨 앞**에 두는 것이 좋다 (사용자 확인, 2026-10-04).
- **네거티브 프롬프트는 안 먹는다** (사용자 경험). 네거티브 기능은 만들지 않는다.

## 1. 공식 근거 (✅ 공식 저장소 원문을 직접 받아 읽음)

출처: `krea-ai/krea-2` 저장소의 `README.md`, `docs/prompting.md`, `docs/expansion.txt` (raw.githubusercontent.com, 2026-10-04 수신).

### 1-1. 프롬프트 문법 — 공식은 이게 전부다
- "자연어 프롬프트를 쓰라." 긴 상세 프롬프트가 가장 좋지만, 짧은 프롬프트도 고품질이 나온다.
- **글자 렌더링은 렌더할 단어를 따옴표로 감싼다.**
- 터보는 최대 2k 해상도까지 가능하다.
- 긴 프롬프트가 필요하면 `expansion.txt`를 LLM의 시스템 프롬프트로 쓰라고 안내한다.
- **공식 문서에 가중치 문법, 네거티브 프롬프트 문법, 태그 문법, 고정된 구조 순서는 없다.**

### 1-2. 공식 예시 20개의 공통 패턴 (✅ 원문 예시에서 관찰, 규칙으로 명시된 것은 아님)
두 가지 형식이 섞여 있다. 둘 다 공식 예시다.
- **쉼표 구절형**: `3D rendered matte black designer toy figure, stylized round ..., studio lighting, solid vibrant blue background, high contrast minimal composition`
- **서술 문장형**: `A close-up portrait of a young East Asian woman with straight black hair... She wears... The background is a solid, striking crimson red. Soft, directional studio lighting...`
- 매체/스타일을 앞이나 첫 문장에 둔다(`3D rendered`, `vintage analog collage`, `close-up anime portrait of`, `A macro photograph`).
- 구체적 재질, 색, 구도(`extreme low-angle`, `high-angle wide perspective`, `shallow depth of field`), 조명(`soft directional studio lighting`, `golden hour`)을 구체 서술로 적는다.
- `masterpiece`, `8k`, `best quality` 같은 품질 태그는 공식 예시에 하나도 없다.

### 1-3. 공식 프롬프트 확장 규칙 (`expansion.txt`) — 이 프로그램의 설계 기준으로 가장 쓸모 있음
1. 충실성 우선: 원래의 피사체·행동·색·공간관계를 보존, 암시되지 않은 물체·인물·동물을 추가하지 않는다.
2. 파싱 쉬운 구조: 피사체별로 속성과 행동을 묶고, 포즈·상호작용·공간배치는 구체적으로 쓴다.
3. 스타일 계획은 내부에서만: 계획 태그나 래퍼를 출력에 넣지 않는다.
4. 글자: 정확한 문구를 쓰고 따옴표로 감싼다.
5. 과도한 구체화 금지: 입력이 뒷받침하지 않으면 옷·색·재질·장면 디테일을 지어내지 않는다.
6. 구조: 한 단락의 일관된 글. 불릿·JSON·마크다운 금지.
7. 이미 상세한 프롬프트는 다듬기만 한다.
8. 인물은 존엄하게 다룬다. 의복이 생식기와 친밀 부위를 덮는 것으로 가정한다.
9. 사용자가 지정한 매체(photo of, illustration of, painting of, sketch of, 3D render of 등)는 존중하고 다른 매체로 바꾸지 않는다.

### 1-4. 모델·샘플러 설정 (✅ README)
| | Raw | Turbo |
|---|---|---|
| 용도 | 베이스·LoRA 학습용 | 8스텝 증류, 일반 추론용 |
| steps | 52 | 8 |
| CFG | 3.5 | **0.0 (비활성)** |
| mu | — | 1.15 |
| 해상도 | 최대 1k | 1k ~ 2k |

- 공식 권장: **Raw로 LoRA를 학습하고 Turbo에서 적용**한다.
- **Turbo는 CFG가 꺼져 있어서 네거티브 프롬프트가 사실상 작동하지 않는다.** 이건 공식 문서에 네거티브 문법이 없다는 사실과 CFG 0.0 설정에서 도출한 추론이다(공식이 "네거티브 불가"라고 명시한 문장은 못 찾음).

## 2. 제3자 자료 (🟡 공식 아님, 신뢰도 낮은 순으로 사용)

- 텍스트 인코더가 Qwen3-VL(언어모델)이고 CLIP/T5가 아니라서 태그 나열보다 자연어가 낫다. 여러 블로그가 같은 설명을 한다. 공식 README의 "자연어 권장"과 방향은 일치하지만 인코더 구성은 공식 원문에서 직접 확인 못 했다. (ComfyUI 워크플로 자료에는 `qwen3vl_4b` 인코더 파일이 쓰인다.)
- 30~150단어가 효과적이라는 수치는 제3자 가이드의 값이다. 공식에는 길이 수치가 없다.
- 구조 순서 "주제+맥락+구도+조명+스타일+크롭" 같은 권장은 블로그마다 다르다. 공식 규칙이 아니라 관례다.
- `(키워드:1.5)` 가중치 문법은 **ComfyUI 커스텀 노드(Krea2PromptWeight)의 기능**이고 모델 고유 문법이 아니다. 해당 자료도 이걸 "Krea 2 네이티브가 아니다"라고 쓴다. 다른 자료는 "가중치 문법 미지원, 다시 서술하거나 LoRA 강도를 쓰라"고 한다.
- 캐릭터 LoRA 트리거는 모델 카드마다 위치 지침이 다르다. "주제 설명 앞쪽 근처", "맨 끝" 둘 다 보인다. 공식 규칙이 아니라 각 LoRA 제작자의 권고다.
- 인물이 4~5명을 넘으면 인물별 속성 충실도가 떨어진다는 보고가 있다(제3자 노드 문서).

## 3. 현재 프로그램(v10.0.2)과 조사 결과의 대조

- ✅ 품질 태그(`masterpiece`, `8k`, `best quality`)는 본체 코드에 없다. 공식 방향과 일치.
- ✅ 재질·조명·카메라를 구체 서술로 넣는 설계는 공식 예시 방향과 일치.
- ⚠️ **LoRA 트리거를 항상 "첫 토큰"으로 출력**하는 규칙은 공식 근거가 없다. LoRA별 모델 카드 지침(앞/끝)이 갈리므로, 사용자가 LoRA별로 위치를 고를 수 있게 하는 편이 안전하다. (확인 대상, 변경은 승인 후)
- ⚠️ 프로그램이 만드는 문장 구조(구절형인지 서술형인지)와 길이를 공식 예시 기준으로 점검할 필요가 있다.
- ⚠️ 글자 렌더링(따옴표) 입력 경로가 있는지 확인 필요.
- ⚠️ 네거티브 프롬프트 기능이 있다면 Turbo(CFG 0)에서 무효라는 점을 UI에 표시할지 검토.
- 위 항목은 본체 3,620줄을 통독하지 않고 grep으로만 확인한 것이라 전수 점검이 아니다.

## 추가 조사 (2026-10-04, 빛·소재·부정문·학습 캡션)
질문: (1) 빛이 소재에서 어떻게 변하는지 결과를 적어야 하나, (2) 문장 안의 부정 표현이 먹나, (3) 색은 추상어 vs 구체 기준, (4) 모델이 어떤 문장으로 학습됐나.
읽은 정도: ✅ 원문 직접 읽음 / 🔎 검색 결과 요약만 봄(원문은 네트워크 차단으로 못 읽음).

### 공식 (✅ `krea-ai/krea-2` 저장소 원문 — 앞서 확인)
- 빛·소재·부정문에 관한 규칙은 **없다.** 공식 문법은 "자연어", "글자는 따옴표", 확장 규칙(지어내지 말 것, 지정한 매체 유지) 뿐이다.

### 빛과 소재 (🔎 제3자 가이드 여러 곳이 같은 방향)
- "광원, 방향, 성질, 대비를 구체적으로 적어라." 소재는 "무엇으로 만들어졌고 빛과 어떻게 만나는지"를 물리적으로 쓰면 렌더러에 줄 재료가 된다는 설명이 반복된다.
- 예시로 인용되는 문장은 `brushed aluminium under hard overhead light` 형태다. 즉 **소재 + 광원**을 적고, 그 결과(하이라이트가 어떻게 생긴다)를 적지는 않는다. 사용자 원칙(소재와 광원만, 반응은 모델에)과 같은 방향이다.
- "결정적인 광원 하나와 제한된 소재 어휘를 쓰라"는 조언이 있다. (✅ `Andro-Meta/krea-2-local-studio` 가이드 원문: 구체적 광원 이름, 소재 상태 예 `damp fabric texture`, `worn wood textures`, 순서 `subject + setting + composition + lighting + mood + medium + texture`, 길고 형용사 나열은 흐려진다.)
- 평가 형용사(`beautiful`, `8k`, `masterpiece`)보다 구체 서술이 낫다는 점은 모든 자료가 일치한다.

### 부정 표현 (🔎 엇갈림)
- 두 개 이상의 제3자 가이드: "문장 안의 `no hat`, `without a beard`는 효과가 없으니 원하는 것을 긍정으로 쓰라(`flat land`, `desolate`)."
  단, 그 이유로 "Turbo는 CFG 1.0이라 부정 분기가 꺼진다"를 드는데 이는 **별도 네거티브 입력란**의 이유이지 문장 속 부정과는 다른 문제라서 근거가 섞여 있다.
- 반대 사례: 같은 계열 가이드(✅ Andro-Meta)가 `avoid illustration, painting, cartoon...`처럼 문장 속 제외 표현을 쓰고, 사용자 프롬프트(C, D)도 `no hair hangs down...`, `no smoothing and no retouching`을 써서 효과를 봤다.
- 별도 네거티브 입력란: Turbo에서 효과 없음이 맞다. 되살리는 서드파티 노드(**ComfyUI-Krea2-NAG**, 🔎 검색 결과로만 확인)가 있다. 사용자가 원하면 검토 가능.
- 결론: 문장 속 부정은 **보증은 없고, 긍정 서술을 주로 쓰고 닫는 문장으로 보조**하는 현재 방식이 가장 안전하다.

### 가중치 (🔎)
- `(키워드:1.5)`는 ComfyUI 커스텀 노드 기능이고 모델 기본 문법이 아니다.

### 인코더·학습 캡션 (🔎 요약만, 확정 아님)
- 텍스트 인코더는 Qwen3-VL-4B-Instruct, 여러 레이어의 특징을 합쳐 쓴다(✅ musubi-tuner 문서: 인코더 이름만 확인, 프롬프트 형식 안내는 없음).
- 학습 캡션이 자연어, 태그, JSON까지 여러 길이와 형식으로 만들어졌다는 설명은 요약 결과로만 봤고 원문은 못 읽었다. 그대로 믿지 않는다.

## Krea 2 기술 보고서 (✅ 사용자가 원문을 붙여줌, 2026-06-23 발행) — 확인된 것
출처: https://www.krea.ai/blog/krea-2-technical-report (전문은 저작권 때문에 저장하지 않고 요점만 적는다)

### 학습 캡션 (프롬프트 쓰는 법의 직접 근거)
- 학습 캡션은 "이미지를 **조밀한 시각 디테일**로 묘사하는 길고 풍부한 자연어 캡션"이다. OCR 결과와 메타데이터(카메라 설정, 알려진 개체 등)를 받아 만든다.
- 그 긴 캡션을 더 싼 LLM이 **여러 길이와 형식**으로 다시 쓴다. **주로 긴 캡션으로 학습하고**, 짧은/중간 길이도 학습 내내 노출된다.
- 프롬프트 확장기 절: "조밀한 프롬프트가 안정적으로 더 좋은 결과를 낸다. 다만 사용자는 학습 캡션 같은 프롬프트를 거의 안 쓴다."
- → **길고 조밀한 자연어 묘사가 학습 분포에 가장 가깝다**는 공식 근거. 캡션은 "이미지에 보이는 것을 서술"하는 글이라, 지시문/메타 명령(`scale lock is enabled` 같은)은 분포 밖이다.

### 텍스트 인코더와 위치 (이전 가설을 약화시킴)
- 인코더: Qwen3-VL. 마지막 층 대신 **여러 층의 특징을 합치는 얕은 어텐션 층**을 쓰고, 토큰 축으로 **가벼운 양방향 트랜스포머 층**을 더해 "자기회귀 편향을 줄인다"고 명시.
- DiT에서 **텍스트 토큰의 RoPE 위치 인덱스는 0**이다.
- → "앞에 적은 것이 더 강하게 먹는다"는 내 가설(앞쪽 얼굴 묘사가 뒤의 전신 지시를 눌렀다)은 **구조상 근거가 약해졌다.** 위치보다는 항목이 너무 많아 신호가 희석되거나, 서로 충돌하는 쪽이 더 그럴듯하다. 핵심 지시를 앞에 두는 것이 해롭진 않지만 원인이라고 단정하지 않는다.

### 프롬프트 충족 학습 (RL)
- 프롬프트를 **검증 가능한 요구사항으로 쪼개** 이미지가 만족했는지 보는 루브릭 보상으로 RL을 했다. 손가락/팔다리 같은 구조 오류용 보상도 따로 있다.
- → 인원수, 위치, 속성처럼 **확인 가능한 요구를 명시적으로 쓰는** 사용자 방식(`exactly one man and exactly one woman`, `sits on the left`)에 학습이 맞춰져 있다.

### CFG와 부정
- RL 단계는 CFG 없이 학습했고, 추론 때 CFG는 선택 옵션이다. **Turbo는 가이던스 증류**를 했다 → Turbo에서 별도 네거티브 입력란이 안 먹는 이유와 일치. (CFG를 쓰는 Raw에서는 네거티브가 동작할 수 있다. 사용자 체크포인트는 Turbo 계열.)
- 문장 속 부정 표현에 대한 직접 근거는 보고서에 **없다.**

### 형식
- 보고서 결론부: 사용자들은 자연어, 태그, JSON, 바운딩 박스, 지시문, 마크다운 등 다양한 방식으로 쓰고, 모델이 이를 **원래 이해하는 것이 앞으로의 과제**라고 한다 → 현재는 자연어가 가장 안전.

### 보고서에 없는 것
빛과 소재의 상호작용 서술법, 문장 속 부정문의 효과, LoRA 트리거 위치, 색 표현 방법은 다루지 않는다. 이 항목들의 근거는 여전히 제3자 자료와 사용자 실측이다.
